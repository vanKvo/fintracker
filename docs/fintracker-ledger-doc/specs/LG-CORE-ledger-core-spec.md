# 3. Ledger Service
This service functions as the synchronous, ACID-compliant System of Record for all core financial data.

## Module 1: Cross-Cutting Core Architecture & Security
### REQ-1.1: Multi-Tenant Data Isolation and API Scoping
**Purpose**:To satisfy the fundamental security premise that "all data is shown based on what user logs in," the system must enforce bulletproof, programmatic API gateway and database-level multi-tenant scoping to prevent unauthorized cross-tenant data access or information leakage.

**Functional Requirements**:
- Inbound Token Extraction: The API Gateway must intercept incoming traffic, validate the user's Cognito JSON Web Token (JWT), query the internal Identity Mapping service to locate the corresponding internal user UUID, and forward it downstream via a custom HTTP header named X-Internal-User-Id.
- Controller-Level Consumption: All Java Spring Boot REST Controllers (including but not limited to TransactionController and DashboardController) must extract and consume this internal identity using the web binder annotation: @RequestHeader("X-Internal-User-Id") UUID userId.

**Non-functional Requirements**:
- Repository Query Restricting: Database access objects and repositories, starting with AccountRepository.java and extending to all dependent persistent units, must restrict all compiled jOOQ SELECT, UPDATE, and DELETE statements programmatically by chaining a mandatory .where(ACCOUNTS.USER_ID.eq(userId)) predicate.
- Performance SLA: The gateway token validation and internal UUID resolution layer must introduce a maximum latency overhead of 12ms per request.

The "user-assigned tags" filter criterion below is not — the Tags column and its editing affordance were intentionally disabled (see Module 2.2.2 D), so there is currently nothing to filter by.

**Functional Requirements**:
- Table Population: Populates the primary UI Transactions View table with explicit data attributes mapped from the backend ledger, containing columns for: Date, Merchant, Account, Category, Amount, Status, and Action.
- Dynamic Aggregate Calculations: Dynamically calculates and displays a "Total Amount" aggregation metric that instantly updates based on the current active filter row criteria.

**Non-functional Requirements**:

### REQ-2.2: Execute Row-Level and Bulk Actions (Complete)
**Purpose**:Users require standard ledger maintenance and curation capabilities to modify transactional metadata, correct categorization mistakes, track split purchases, and formally approve pending bank feed data.

**Functional Requirements**:
2.2.1. Inline Row Modification (complete)
A. User Experience: User clicks directly into a ledger table cell to edit category or amount of a transaction.
B. System Action: Validates data input types and fires a patch request to the transactions endpoint.
C. Data Impact: Overwrites target metadata elements (categories, amounts) in the ledger.transactions table.
D. Business Constraints: The categories must be a drop-down list that is defined by the system. The amount must be a valid decimal number.

2.2.2. Tag Array Appending (complete)
A. User Experience: User selects existing tags or types a new tag into a multi-select dropdown component on the transaction row.
B. System Action: Evaluates if the tag is new and appends it to the transaction's tag collection. 
- Duplicate handling: If the transaction has the tag and the user appends the same tag again, then don't append the same tag in the array - the array should have unique values.
C. Data Impact: Updates the tags column, stored natively as a database text array type (text[]).
D. Business Constraints: 
- No leading/trailing space: Custom tags must be stripped of leading/trailing whitespaces and specialized characters before insertion. The tags should be user-scoped.
- Allowable Characters: Specialized characters are alphanumeric, hyphen, underscore only. 
- Case Insensitivity: Tags is insensitive, e.g., "Groceries" the same tag as "groceries" for dedup/search purposes.
- Tag element: Each element in the tag array have max length of 50 chars and max 10 tags for each transactions.

2.2.3. Transaction Splitting (complete)
A. User Experience: User selects a "Split" action, opening a modal to divide a single transaction into two or more line items.
B. System Action: Calculates total balance allocations and the original transaction is hidden.
C. Data Impact: Instantiates new discrete rows in ledger.transactions with their parent_transaction_id columns pointing to the original transaction record's ID.
D. Business Constraints: The sum of child transaction amounts must exactly equal the parent transaction amount. The parent transaction must be dynamically hidden from active views (WHERE NOT EXISTS) the moment child rows are written.

2.2.4. Spending Formula Exclusion (complete)
- User Experience: User toggles an "Exclude from transaction" switch on a specific transaction row.
- System Action: Flags the row to be bypassed by downstream reporting engines.
- Data Impact: Toggles an is_excluded boolean flag to TRUE on the targeted row.
- Business Constraints: Core transaction financial data must remain entirely immutable; exclusion only affects downstream reporting and pacing calculations.

2.2.5. Status Promotion (complete)
- User Experience: User clicks an "Approve" button on a single pending row or checks multiple rows to click a bulk "Approve Selected" button.
- System Action: Processes state transitions for the selected unique transaction IDs.
- Data Impact: Transitions the internal state of the status column from 'PENDING' to 'POSTED'.
- Business Constraints: Only transactions currently in the 'PENDING' state are eligible for promotion.

**Non-Functional Requirements**
- Atomic Integrity (ACID): Split and update behaviors must run in an ACID isolated database transaction block to guarantee that parent-child allocations are never saved in an unbalanced or corrupted state.

### REQ-2.3: Manage Manual Entries (Complete)
**Purpose**:To guarantee a completely unified and accurate net-worth picture, users must be able to log manual expenses (such as cash purchases) that do not appear on automated financial account feeds, while protecting system-synced records from arbitrary deletion.

**Functional Requirements**:
2.3.1. Manual Row Insertion (complete):
A. User Experience: The user goes to Transactions tab, click on "Add Transaction" button to manually insert a transaction. 
B. System Action: 
- Basic Flow: The transaction dialog pops up and prompts the user to input required files (Date, Account, Amount, Category, Merchant, Type), while allowing the optional fields to be blank or to default values. After the user clicks on "Save" button, the dialog disappears and the transaction is shown in the transaction 
view table. 
- Missing required fields/Bad data: If the user is missing the required fields, the system let the user know which required fields are missing and doesn't allow the user to save the transaction. If the user has data inputs that violates business contraints, the system let the user what data the system requires so the user can fix it.
C. Data Impact: The manual transaction is saved in the database with its source column as MANUAL_ENTRY and its is_manual column marked as true by default.
D. Business Contraints: 
- Date: Default to today's date. The user can select other dates as needed.
- Account: Show the dropdown list of existing bank accounts associated with the user. The user can select "Create New Bank Account" button, which will direct them to "New Bank Account" popup, which is implemented in the Accounts module. Only accounts belonging to the requesting user may be selected or accepted by the backend — the backend must independently validate account ownership regardless of what the dropdown displays.
- Category: The system's dropdown list of categories.
- Amount: Decimal numbers only.
- Merchant: Required. Free text identifying who the transaction was with.
- Type: Required. Either PURCHASE or CREDIT.
- Status: POSTED
- Source: MANUAL_ENTRY

2.3.2. Conditional Hard Delete Protection (complete):
A. User Experience: The user clicks on "Delect transaction" in in-line row editing.
B. System Behavior: The system only allows deleting transaction if the is_manual sets to be true. 
C. Data Impact: The manual transaction entered by the user will be deleted from the transactions table in the database.
D. Business Contraints: Bank statements upload ingestions, automated or synced bank rows containing an is_manual flag of false must block all hard-delete API network requests to maintain data integrity - the delete function will be disabled for these transactions not entering manually by the user.

### REQ-3.3: MANUAL and AUTOMATED sync modes (Not Implemented)
**Status note**: The Ledger Service's own responsibility here is a no-op by design — the Data Ingestion Service owns the ETL from bank statement upload / bank sync into ledger.transactions, and the Ledger only ever reads already-tagged rows for its own compute and logic. None of the UI behavior below (Upload Statement popup account graying, the AUTOMATED→MANUAL warning dialog) is built — the Upload Statement modal in fintracker-ui is still a hardcoded, unwired stub with no awareness of account sync mode. Only the DB-level constraint (D, one sync mode per account) is genuinely enforced today.

A. User Experience: The user will choose either "MANUAL" or "AUTOMATED" from the Sync Mode data field.
B. System Behavior:
- "MANUAL" selection: If the user selects "MANUAL" for a bank account, the bank account will be shown as one of the selections in the "Upload Statement" popup and its automated function will be disabled if the account is currently "AUTOMATED", which is registered as automatically synced transactions from its bank. Show the warning popup to the user when they change from "AUTOMATED" to "MANUAL" so that they are aware of this system behaviour. 
- "AUTOMATED" selection: If the user selects "AUTOMATED" for the account, the bank account will be grayed out, cannot be selected, and "(AUTOMATED)" shown next to it in the account selection in "Upload Statement" popup.   
C. Data Impacts:
- "MANUAL" selection: Transactions ingested through "Upload Statement" will have their "source" as "STATEMENT_UPLOAD", "status"
 as "PENDING", "is_manual" as "FALSE". 
- "AUTOMATED" selection: Transactions ingested through bank sync will have their "source" as "BANK_SYNC", "status" as "POSTED", "is_manual" as "FALSE". 
D. Business Contraints: The system only allows either "MANUAL" or "AUTOMATED" sync mode for a single bank account.

### REQ-4.3: Downloading an Original File

B. System Behavior: The system searches for the file location in the database, which is a file key for document stored in AWS S3, and provide a downloaded file to the user.
C. Data Impact: The file is retrieved from AWS S3. No change occurs in the database.
D. Business Contraints: The file must be downloaded securely and cached in-memory during the user's session only. It must not persist on the user's device after the session ends.
E. Technical design:
- S3 Access: Do not expose raw S3 URLs. Access must be gated via short-lived AWS S3 Presigned URLs (maximum 15-minute expiration).
- Browser Cache Control: Serve the file with HTTP headers to prevent local disk caching: `Cache-Control: private, no-store, no-cache, must-revalidate`
- Session Caching: Implement frontend-side state caching. Upon the first download request, fetch the file as a Blob, create an Object URL (`URL.createObjectURL`), and store it in the application state. Subsequent download actions within the same session must resolve from this state rather than initiating a new S3 API request.

- Metadata Table Feeding: Extracts operational metadata properties from ledger.statements to populate the file-vault interface, detailing storage paths, verification states, upload timelines, and linked financial accounts.

- Asynchronous Completion Auditing: Registers an active operational hook that monitors transaction postings. When a transaction transitions into 'POSTED', the system queries for any remaining 'PENDING_APPROVAL' transactions bound to that statement. If the pending count hits zero, the parent statement status is automatically advanced to 'COMPLETED'.

## Module 5: Budgets
### REQ-5.1: Manage Time-Series Budgets and Progress Pacing
**Purpose**:Active pacing charts give users immediate clarity on current spending run rates against predetermined monthly category thresholds to foster disciplined financial decision-making.

**Functional Requirements**:
- Visual Progress Indicators: Calculates and supplies metrics to render visual category progress bars and pacing indicators inside the main Budgets View.
- Data Lifecycle Persistence: Creates or updates records across the dual ledger schemas ledger.budgets and ledger.budget_lines, locking the temporal effective_month property to the first calendar day of the month (YYYY-MM-01).
- Auto-Template Copying: Instantiates a default monthly configuration template automatically by copying active budget categories and limits from the immediately preceding calendar month whenever a user navigates into a brand new month lacking a pre-existing budget structure.

**Non-functional Requirements**:
- Historical Integrity Protection: Enforces an absolute, immutable read-only state for all past historical months to block retrospective modifications and preserve audit accuracy.

**Purpose**:An intelligent exception engine guides user focus by bubbling up tasks that require immediate manual resolution, such as reviewing data anomalies or category spending overruns.

**Functional Requirements**:
- Review Queue Identification: Continually monitors data states to identify unreviewed pending transactions requiring manual oversight.
- Budget Overrun Extraction: Compares active spending levels against the defined limit_amount fields declared in ledger.budget_lines to pinpoint exact budget lines suffering from over-limit states.
- Alert Hub Synthesis: Consolidates these exceptions into actionable, high-priority notifications presented directly within the Dashboard Action Hub.

**Non-functional Requirements**:
- Scope Limitation Directive: Automated real-time transactional bank account feed synchronization is explicitly excluded and deferred for Phase 1. All alerting calculations must rely on manually inputted entries or uploaded transaction states.
