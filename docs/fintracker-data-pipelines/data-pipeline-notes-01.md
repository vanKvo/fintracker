# Data Pipeline — Implementation Notes (REQ-DP-01, REQ-DP-02, and error handling)

This records what changed in `services/fintracker-data-pipeline`, why, and
what production-readiness practices are now in place versus still open.
Written against the code as implemented, not the aspirational interfaces
sketched in `data-pipeline-spec-01.md` — a few signatures diverged once
real constraints (Step Functions semantics, PDF text-layer access) forced
a decision; those divergences are called out explicitly below.

## 1. What changed

### REQ-DP-01 — Hardening Imports
- **CSV bank-column mapping**: `gatekeeper/mapping_repository.py` (DynamoDB, one item per `bank_id`) + `gatekeeper/bank_mapping_baseline.py` (static seed parsed from the pre-existing `bank_mappings.json`, 9 usable banks — Citibank's split debit/credit columns don't fit the single-`amount`-field model and are intentionally excluded, not silently mishandled). `propose_column_mapping` matches a CSV's real headers against the merged baseline+DynamoDB mapping; `confirm_column_mapping` writes the user's confirmation back to DynamoDB (self-correcting: the second upload from a bank is fully automatic even if the first one needed manual mapping).
- **Mapping confirmation as a real pause, not a client-side step**: the Gatekeeper Step Functions task uses AWS's `waitForTaskToken` integration. For CSV, the execution genuinely pauses — `gatekeeper/mapping_confirmation_handler.py` (a separate, API-Gateway-invoked Lambda) is what resumes it later via `send_task_success`. This is why the state machine had to move from `EXPRESS` to `STANDARD` (Express workflows cap total execution at 5 minutes; a user reviewing a dialog can take longer, and Standard supports up to a year).
- **Closed the confirmed CSV dead-end** (`csv_s3_key` produced, never consumed): `parse_csv_transactions` now takes the confirmed mapping and actually runs.
- **Tier 1 (PyMuPDF text layer) → Tier 2 (Textract) waterfall**: `extract_from_text_layer` reads a PDF's own text directly — no OCR, no per-page cost — for the (common) case of a digitally-generated statement. Only pages it can't parse fall through to Textract's `AnalyzeDocument(FeatureTypes=["TABLES"])`, which classifies and extracts a page in the same call (no separate vision-classification step — this is also what let YOLO come out entirely: `ultralytics`/`torchvision` are gone from `pyproject.toml`).
- **Confidence scoring**: every `RawTransaction` carries `extraction_tier` and `confidence` (CSV 1.00 > text layer 0.95 > Textract 0.75, with a stricter 0.55 for screenshots specifically — a single photo has no multi-page context and is the likeliest format to be blurry or mis-rotated). `NormalizedTransaction.needs_review` is set when confidence falls under a threshold; no new Ledger status was introduced, per the spec's own constraint — `needs_review` rides alongside the existing `PENDING_APPROVAL`.
- **REQ-DP-04 resource caps** (file size, PDF page count) enforced in the Gatekeeper before any paid inference.

### REQ-DP-02 — Parallel Processing
- **Tier 2 page extraction**: `_run_tier2_concurrently` runs `classify_and_extract_page` across pages on a bounded `ThreadPoolExecutor` (Textract calls are I/O-bound; the GIL releases during the socket wait, so threads give real concurrency here without needing `asyncio`). One page's failure is caught and logged individually — it doesn't block the others, and the job isn't failed unless every page comes back empty.
- **Ledger push**: `push_transactions_to_ledger` submits all transactions concurrently, same reasoning. Throttle responses (429/503) get per-request retry with exponential backoff (`tenacity`); a transaction that never gets through is counted in `total_count`, not `success_count` — it doesn't block or fail the batch.
- **Tier skipping at scale**: when Tier 1 fully covers a PDF, Tier 2/Textract is never invoked for that document at all. This is the actual cost lever, not the per-call concurrency — see §4 below.

### Error handling (this and the prior session, together)
- `shared/exceptions.py`: a `PipelineError` hierarchy with a stable `.reason` code on every exception, so a handler can record *why* a job failed without parsing free text, and the reason is assertable rather than string-matched.
- Every Lambda handler (`gatekeeper`, `extractor`, `normalizer`, `data_dispatcher`) wraps its call in try/except, records `PipelineStatus.FAILED` with the reason, then re-raises. Previously an exception left a job's status stuck at whatever it last was — silently forever, since nothing ever set it to `FAILED`.
- Fixed a real bug: the Ledger-push handler used to mark every job `COMPLETED` regardless of how many transactions actually succeeded. It now reports `COMPLETED` / `PARTIALLY_COMPLETED` / `FAILED` based on the real outcome.
- Fixed a real bug: a failed Ledger push used to log the full transaction body (merchant, amount, account fields) as part of the error log line. It now logs only the error and `job_id`.
- **Step Functions-level failure handling** (`infrastructure/pipeline_stack.py`): every task now has a `Catch` block, so a failure surfaces to the *execution* (visible in the Step Functions console / CloudWatch), not only to the Job Tracker — the two were previously only connected by the handler's own try/except, with nothing at the orchestration layer.
- **A genuine correctness bug caught while wiring the callback pattern**: with `waitForTaskToken`, a Lambda's return value does *not* resolve the state — only an explicit `SendTaskSuccess`/`SendTaskFailure` call does. The Gatekeeper handler now calls these explicitly for every outcome (success, pause, and failure); simply returning would have left every non-paused execution hanging until the task timeout fired.

## 2. Reliability practices

- **Idempotent execution names**: the S3 processor now mints a `job_id` (UUID) *before* calling `start_execution` and uses it as both the execution name and the value inside the state machine's own input. Step Functions execution names must be unique per state machine — a duplicate S3 event (they're at-least-once by design) now fails to start a second execution with the same name instead of silently running the pipeline twice. This closes the duplicate-Ledger-push risk at the point closest to its actual cause, rather than only downstream at the Ledger API.
- **Partial-failure isolation everywhere concurrency was added**: one page or one transaction failing is caught, logged, and excluded from the batch's success count — never allowed to raise an exception that kills the whole `ThreadPoolExecutor.map`/`wait` call and discards every other page/transaction's already-completed work.
- **Retry with backoff, not retry with a fixed delay**: both Textract calls and Ledger pushes use `tenacity`'s exponential backoff, capped at a small number of attempts — appropriate for throttling (which needs increasing delay) and inappropriate to apply to, say, a malformed-request error (which retrying will never fix — those aren't wrapped in `retry_if_exception_type`/`retry_if_exception` at all).
- **Preserving state across an asynchronous pause**: the Gatekeeper task's `result_path` (not the default full-state replacement) keeps `bucket`/`user_id`/`statement_id`/`account_id` alive across the mapping-confirmation pause, which can be resumed by a completely different Lambda invocation, possibly minutes or hours later. Getting this wrong (using the task's raw output as the new state) would have silently dropped every field the resumed execution needs.

## 3. Security practices

- **Tenant scoping on the Ledger push** (REQ-DP-06): `X-Internal-User-Id` is now forwarded on every internal Ledger call, alongside the existing internal API key. Previously the Ledger's `UserContextFilter` had nothing per-request to scope against except whatever `user_id` happened to be embedded in the transaction body — the exact "trust a client-supplied ID" pattern this project's own `CLAUDE.md` explicitly disallows.
- **Secrets via SSM, not environment variables**: `INTERNAL_API_KEY` now reads through `core/config.py`'s `SSMProvider` (`SecureString`, 5-minute in-memory cache) instead of a plain Lambda environment variable. An environment variable is visible to anyone with `lambda:GetFunctionConfiguration` on the function and isn't rotated independently of a deployment — this was a real deviation from the project's own Python standards ("Secrets via AWS SSM Parameter Store, never hardcoded") that predates this change and is now fixed. IAM was scoped to read only that parameter path, not `ssm:GetParameter` broadly.
- **PII/log hygiene** (REQ-DP-08): raw transaction content (merchant, amount, any account fields) is never logged, including on failure — only IDs, counts, and status. This was a real gap (the failure-path log line used to include the full transaction dict) closed as part of this work.
- **Least-privilege IAM, where the AWS API actually allows it** (REQ-DP-07): Comprehend's `ClassifyDocument` is now scoped to the specific classifier endpoint ARN instead of `resources=["*"]`. Textract's `AnalyzeDocument` is left as a documented exception — the action genuinely doesn't support resource-level ARN scoping, so a wildcard there is the ceiling of what IAM allows, not an oversight.
- **Task tokens are handled as sensitive**: the Step Functions task token is only ever written to (never logged from) the Job Tracker record, and is only usable to resume the one specific paused execution it belongs to.

## 4. Scalability & cost practices

- **Tier skipping is the real cost lever, not per-call parallelism.** A digitally-generated PDF (the common case) now never touches Textract at all — Tier 1 reads the text layer directly. Concurrency on Tier 2 only matters for the pages that *do* need OCR; it reduces latency, but the tiering is what reduces spend as upload volume grows.
- **Bounded concurrency, not unbounded fan-out.** Both `_MAX_CONCURRENT_TEXTRACT_CALLS` (8) and `_MAX_CONCURRENT_PUSHES` (10, configurable via `MAX_CONCURRENT_LEDGER_PUSHES`) cap how many requests one Lambda invocation issues at once. Textract and most internal APIs enforce their own account-level or per-second limits; an unbounded `ThreadPoolExecutor` for a 50-page statement would just convert Lambda-side concurrency into Textract-side throttling, with strictly worse latency and no cost benefit. The bound is a constant today — see §5 for why an adaptive version is a follow-up, not done here.
- **Resource caps before any paid work**: file-size and page-count limits are enforced in the Gatekeeper, before Tier 1/Tier 2/Comprehend are ever reached — REQ-DP-04's actual point (a single oversized upload shouldn't be able to run up account-wide spend).
- **`STANDARD` Step Functions, not `EXPRESS`**: this is also a cost trade, not just a duration one — Standard bills per state transition, appropriate for a workflow that spends most of its wall-clock time genuinely idle (waiting on a human), rather than per-invocation/duration like Express, which assumes the workflow is actively running the whole time it's billed for.

## 5. What's still open (explicitly not done here)

Being direct about the gap between "implemented" and "production-hardened enough that I'd stop watching it":

- **API Gateway + Cognito authorizer wiring for `mapping_confirmation_handler`** isn't in this change — only the Lambda itself. It must sit behind the same JWT/`X-Internal-User-Id` trust boundary as every other user-facing route (REQ-DP-05) before it can go live; right now it's a function with no front door.
- **Deploy-time DynamoDB seeding for the bank mapping baseline.** `bank_mapping_baseline.py` re-parses `bank_mappings.json` on every cold start via `functools.lru_cache` — correct, but re-parsing a bundled file isn't the idiomatic AWS pattern for seed data. A CDK custom resource (or a one-off migration Lambda run at deploy time) that loads it into DynamoDB once is the more standard approach, and would also let the baseline itself be corrected without a redeploy.
- **Adaptive concurrency, not just a static cap.** REQ-DP-02's own error-handling section calls for "back off and retry with *reduced* concurrency" on `LEDGER_THROTTLED`. What's implemented is a fixed-size pool plus per-request retry — which handles throttling correctly, but doesn't shrink the pool size in response to it. A sustained throttle burst will retry every in-flight request in the batch rather than easing off first. Worth adding if throttling shows up in practice; not worth the complexity pre-emptively.
- **A stronger idempotency key at the Ledger API itself.** The execution-name fix (§2) prevents a *duplicate S3 event* from starting a second execution. It does not prevent a *retried Step Functions task within one execution* (e.g., a Ledger-push Lambda that times out after the Ledger already received the request) from re-posting the same transactions. REQ-DP-03 calls for the Ledger's internal endpoint to accept/generate an idempotency key derived from `statement_id`; that's a Ledger-service-side change, out of this pipeline's own codebase, and is the one piece of REQ-DP-03 not closeable from this side alone.
- **No encryption-at-rest configuration was touched** (S3 bucket KMS, DynamoDB table encryption) — this change didn't touch bucket/table provisioning at all, so whatever the existing baseline is, it's unchanged, not verified.
- **Per-tenant rate limiting** (a noisy-neighbor upload burst from one user affecting Lambda concurrency for everyone) is still open — REQ-DP-04's caps limit a *single upload's* cost, not a tenant's aggregate upload rate.
- **The spec's literal `classify_and_extract_page(bucket, page_key)` two-argument signature** couldn't be implemented as written: extracting a specific PDF page needs the *original PDF bytes* and a page index, not just an S3 key, and whether a page is a screenshot (stricter confidence) versus a PDF page isn't derivable from the key alone. The implemented signature is `classify_and_extract_page(bucket, s3_key, page_num, is_pdf, is_screenshot)` — noted here since a spec interface and its implementation silently diverging is worse than flagging it.
